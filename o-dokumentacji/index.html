#3.0:. LEKTURA O LEKTURZE

#WSTĘP

Niestety lekka metoda działania, jaką wprowadziło DENO, niebawem może zniknąć, gdyż w październiku 2026 roku zostało ono przejęte przez CLOUDFLARE i już wiadomo, że nie będzie wersji 3.0, a jedynie zapowiedziane na rok łatki — to wielki cios. Deno oferowało po wyjęciu z pudełka wsparcie dla TypeScript (obecna wersja to 7.0.2, a nowością w tej wersji jest całościowe przepisanie go na język Go). Oferowało też wsparcie dla React i Preact, np. przy użyciu Hono, bez zbędnego, ciągłego przebudowywania wszystkiego na czysty JavaScript. Dodatkowo dzięki JSR oraz esm.sh można było całkowicie pozbyć się syfu NODE i studni bez dna, zakrzywiającej czasoprzestrzeń bardziej niż czarna dziura — folderu node_modules. Powstał fork Ende, ale zobaczymy, co przyniesie. Równocześnie mam też własną koncepcję, https://github.com/j-Cis/tsxr, mającą na celu zastąpienie Deno.

Stan obecny: wszystko działa pod Deno. Ende jest odłożone — miało zastąpić Deno, ale jeszcze nie działa. Docelowo cały folder web/ przejmie tsxr, którego jeszcze nie ma.

#JAK TO DZIAŁA

Droga od pliku do strony w przeglądarce, krok po kroku:

  1. deno task czytaj uruchamia serwer z pliku web/main.tsx. Serwer to Hono.
  2. Przy starcie serwer przegląda folder site/routes/. Każdy plik index.tsx to jedna strona.
  3. Dla każdej strony serwer od razu składa jej CSS. Bierze go z plików, które ta strona importuje (rozdział STYLE).
  4. Przy starcie serwer przygotowuje też kod dla przeglądarki: web/client.ts, każdą wyspę *.island.tsx z site/client/ i wszystko, co one importują. TS i TSX zamienia na JS. Tylko te pliki przeglądarka może pobrać.
  5. Strony, sekcje i kod serwera nigdy nie wychodzą z serwera. Przeglądarka dostaje z nich tylko gotowy HTML.
  6. Gdy przychodzi zapytanie o stronę, serwer renderuje ją do HTML (Preact) wewnątrz szkieletu PageShell z web/page-shell.tsx.
  7. W nagłówku strony są: CSS strony w <style>, plik /styles.css, mapa importów i skrypt /web/client.ts.
  8. W przeglądarce client.ts szuka elementów data-island i ożywia (hydratuje) wyspy. Reszta strony zostaje zwykłym HTML.

Kolejność obsługi adresu: najpierw strona, potem kod dla przeglądarki, potem plik statyczny z site/static/. Gdy nic nie pasuje, serwer pokazuje stronę 404.

#DWA OBSZARY

FRAMEWORK web/
  • Silnik strony: serwer, trasy, CSS, wyspy, eksport.
  • Nie zawiera nic, co dotyczy tej konkretnej strony.
  • Nie importuje plików z site/. Sam przegląda site/ i z tego buduje stronę.
  • Udostępnia stronie ogólne narzędzia, np. web/island.ts (oznaczanie wysp) i web/heading-anchors.ts (kotwice nagłówków).
STRONA site/
  • Treść i klocki tej strony.
  • Każdy folder ma jedno ściśle określone zadanie (rozdział FOLDERY STRONY).
  • O roli pliku decyduje folder i przyrostek nazwy, np. .widget.tsx.
KONFIGURACJA deno.json i ende.json
  • Dwa prawie identyczne pliki: deno.json dla Deno, ende.json dla Ende.
  • Jedyna obecna różnica to import @transpilacja: w Deno wskazuje web/transpile.ts, w Ende — web/transpile-ende.ts.
  • Są w nich: zależności (imports), polecenia (tasks), ustawienia TypeScript i formatowania.
  • Folder _to_delete/ jest wyłączony (exclude).

#PLIKI FRAMEWORKA

Każdy plik w web/ robi jedną rzecz:

  • main.tsx — serwer. Znajduje strony, składa ich CSS, podaje kod dla przeglądarki, pliki statyczne i stronę 404.
  • page-shell.tsx — szkielet każdej strony: <html>, <head>, <body>.
  • page-shell.css — styl bazowy każdej strony.
  • island.ts — funkcja island(…), która oznacza komponent jako wyspę.
  • client.ts — jedyny skrypt startowy przeglądarki. Ożywia wyspy.
  • transpile.ts — zamienia TS i TSX na JS dla przeglądarki. Tylko dla Deno (@deno/loader).
  • transpile-ende.ts — to samo dla Ende, przez natywny TypeScript (tsgo).
  • style.ts — składa CSS strony w warstwy.
  • importmap.ts — mapa importów dla przeglądarki, zbudowana z adresów w deno.json.
  • staticfiles.ts — podaje pliki z site/static/.
  • refresh.ts — samoczynne przeładowanie strony po restarcie serwera.
  • listwy.ts — mierzy przyklejone listwy (górną i dolną).
  • heading-anchors.ts — unikalne kotwice #id nagłówków.
  • 404.tsx — strona 404 z mapą wszystkich stron.
  • gh-pages.ts — eksport całej strony do plików statycznych w dist/, np. dla GitHub Pages.

#FOLDERY STRONY

STRONY site/routes/
  • Pliki: index.tsx i opcjonalnie index.css obok.
  • Każdy folder z index.tsx to jedna strona. Ścieżka folderu to adres strony.
  • index.css działa tylko na tę jedną stronę.
SEKCJE site/layout/
  • Pliki: <Nazwa>.section.tsx albo <Nazwa>.sections.tsx, obok opcjonalnie CSS o tej samej nazwie.
  • Gotowe fragmenty stron, wypełnione treścią. Można je pisać w index.tsx, ale osobno jest czytelniej.
  • Sekcja może składać się z wielu funkcji wewnętrznych.
  • Bez reeksportów.
WIDGETY site/widget/
  • Pliki: <Nazwa>.widget.tsx albo <Nazwa>.widgets.tsx, obok opcjonalnie CSS.
  • Klocki budulcowe: tabela, akapit, tytuł, listwy. Wszystkie oprócz wysp.
  • Zagnieżdżają się jak matrioszki: widget może używać innych widgetów.
  • Dane dostają z miejsca użycia. Wyjątkiem są stałe, podstawowe słowa.
  • Wszystkie są zebrane w beczce _ANY.ts.
RENDERY site/screen/
  • Pliki główne leżą na górze folderu: <Nazwa>.render.tsx, obok opcjonalnie CSS.
  • Interpreter czyta język (np. LOCI), buduje model i zgłasza błędy. Render zamienia dane albo model (LOCI, DOTX) na HTML, SVG albo Canvas.
  • Części renderu są w podfolderze tematu, małymi literami: loci/, dotx/.
  • Inny kod importuje render przez plik główny, nie przez jego części.
WYSPY site/client/
  • Pliki: <Nazwa>.island.tsx, obok opcjonalnie CSS.
  • Kod, który działa w przeglądarce (hydracja).
  • hooks/ — hooki Preact dla wysp, np. pan-zoom.ts.
  • registries/ — rejestry elementów SVG i Canvas, które może pokazać VectorViewport.
  • Bez reeksportów.
SILNIK site/common/
  • Tylko czysty TypeScript: pliki .ts, bez .tsx i bez importów z preact.
  • Nie importuje z innych folderów site/. Może go używać każdy plik w site/.
  • css/ (np. cx.ts), util/, lang/ (definicje języków LOCI i DOTX), drafts/ (szkice).
  • Język w lang/ to tylko znaczniki, atrybuty i funkcje do wypełniania atrybutów. Interpretacja i rysowanie należą do odbiorcy, np. site/screen/.
  • Tu reeksporty są dozwolone.
PLIKI STATYCZNE site/static/
  • Tylko pliki statyczne: ikona, obrazy, styles.css. Bez kodu.
  • Adres pliku to jego ścieżka w tym folderze: site/static/logo.svg → /logo.svg.
SZKICE site/drafts/
  • Szkice i eksperymenty dotyczące strony.
  • Szkice czystego TypeScript są w site/common/drafts/.

Nowy folder w site/ można dodać, gdy ma własne zadanie, którego nie pokrywa żaden istniejący folder. Jego nazwa ma dokładnie 6 liter, a rozszerzenie Material Icon Theme w VS Code koloruje go bez dodatkowych ustawień.

#NAZWY PLIKÓW

  • Przyrostek decyduje o roli. Plik bez .widget.tsx nie jest widgetem. Plik bez .island.tsx nie jest wyspą. Framework rozpoznaje pliki tylko po tych dokładnych przyrostkach.
  • Komponenty (widgety, rendery, wyspy, sekcje) mają nazwy PascalCase, np. Table.widget.tsx, Loci.render.tsx.
  • Elementy języka w site/common/lang/: nazwa języka wielkimi literami, potem nazwa elementu od wielkiej litery, np. LOCIBodyElement.ts (jeden znacznik) i LOCIDatumAttributes.ts (grupa atrybutów wspólna dla kilku znaczników).
  • Pozostałe pliki (części, pomocnicze, rejestry) mają nazwy małymi literami, z łącznikiem, np. render-svg.tsx, pan-zoom.ts.
  • Pliki w web/ mają nazwy małymi literami, po angielsku, z łącznikiem.
  • Beczka _ANY.ts ma podkreślnik na początku, żeby stała na górze listy plików.
  • Nagłówek. Każdy plik zaczyna się nagłówkiem @project-metadata: ścieżka (Path), autor, repozytorium. Uzupełnia go skrypt inject-metadata.ps1.

#STRONY I ADRESY

Adres strony wynika z miejsca pliku index.tsx w site/routes/:

  • site/routes/index.tsx → /
  • site/routes/o-dokumentacji/index.tsx → /o-dokumentacji (oraz /o-dokumentacji/)
  • site/routes/lang/loci/sandbox/index.tsx → /lang/loci/sandbox
  • Folder bez index.tsx jest tylko członem adresu, np. site/routes/lang/.
  • Nowa strona = nowy folder z index.tsx. Serwer szuka stron przy starcie; czytaj-pisz restartuje go po każdej zmianie.
  • Domyślny eksport index.tsx to komponent strony. Bez niego serwer nie wystartuje.
  • Strona może wyeksportować tytul — to tytuł karty przeglądarki. Domyślnie „LEKTURA”.
  • Strona 404 powstaje sama. Pokazuje adres, którego nie ma, i mapę wszystkich stron z ich plikami.

Najmniejsza strona:

// site/routes/przyklad/index.tsx  →  adres /przyklad
import { P, Title } from "@/site/widget/_ANY.ts";

export const tytul = "PRZYKŁAD";

export default function WebPage() {
	return (
		<main class="page">
			<Title level="h1">Przykład</Title>
			<P>Treść strony.</P>
		</main>
	);
}

#STYLE (CSS)

  • Plik-rodzeństwo. CSS komponentu ma tę samą nazwę co jego .tsx, z tym samym przyrostkiem; różni się tylko rozszerzeniem: Table.widget.tsx → Table.widget.css. Nie trzeba go nigdzie importować.
  • Tylko to, czego strona używa. CSS komponentu trafia na stronę tylko wtedy, gdy jego .tsx jest w grafie importów jej index.tsx (także pośrednio, przez sekcje). Strona bez tabeli nie dostaje CSS tabeli. import type się nie liczy.
  • Beczka po nazwach. Gdy strona importuje z _ANY.ts tylko P i Title, dostaje CSS tylko akapitu i tytułu, a nie wszystkich widgetów z beczki.
  • Warstwy, od najsłabszej: shell (web/page-shell.css), widget (widgety, wyspy, rendery), layout (sekcje), route (index.css strony). Późniejsza warstwa wygrywa bez względu na siłę selektora. Styl strony zawsze nadpisze styl sekcji, sekcja — komponentu, a komponent — bazę.
  • site/static/styles.css jest poza warstwami, więc wygrywa ze wszystkimi. To miejsce na ręczne poprawki.
  • index.css działa tylko na swoją stronę. Podstrony go nie dziedziczą.
  • CSS strony trafia do <style> w jej HTML, a nie do osobnego pliku.
  • Pusty plik CSS może czekać na przyszłe style.
  • CSS bez pliku .tsx o tej samej nazwie nie trafi na żadną stronę. Serwer ostrzega o nim przy starcie.

#KTO MOŻE UŻYWAĆ KOGO

  • Widgety mogą być użyte w stronach, sekcjach, wyspach i w innych widgetach.
  • Rendery mogą być użyte w stronach, sekcjach i wyspach. Render może użyć innego renderu, ale nie jest to zalecane.
  • Wyspy mogą być użyte w stronach i sekcjach.
  • Sekcje mogą być użyte w stronach. Sekcja nie powinna używać innej sekcji (odradzane, nie zakazane).
  • site/common/ i narzędzia z web/ (np. web/island.ts) mogą być użyte wszędzie w site/.

Reeksporty są dozwolone tylko w trzech miejscach:

  • site/widget/_ANY.ts — wszystkie widgety;
  • site/screen/_ANY.ts — rendery;
  • site/common/ — moduły czystego TypeScript mogą reeksportować się nawzajem.

#WYSPY

Wyspa to komponent, który działa w przeglądarce, np. przesuwanie i powiększanie rysunku. Reszta strony to statyczny HTML z serwera. Dzięki temu przeglądarka pobiera tylko kod wysp.

  • Plik site/client/<Nazwa>.island.tsx. Domyślny eksport to island( import.meta.url, Komponent ) z web/island.ts.
  • Na serwerze wyspa renderuje się w <div data-island="…" data-props="…">. W przeglądarce client.ts importuje plik wyspy i ją ożywia.
  • Atrybuty wyspy przechodzą do przeglądarki jako JSON: liczby, teksty, tablice, obiekty. Funkcje i JSX w atrybutach nie przejdą.
  • Takie wejście zamienia na serwerze trzeci argument: island( url, Komponent, prepare ). Uwaga: plik z prepare też trafia do przeglądarki.
  • children wyspy serwer renderuje do HTML. W przeglądarce zostają statycznym HTML i wyspa ich nie przerysowuje. Wyspa zagnieżdżona w środku ożywa sama.
  • Wszystko, co wyspa importuje, idzie do przeglądarki. Dlatego wyspa importuje pliki wprost, nie przez _ANY.ts. Inaczej serwer nie wystartuje i pokaże błąd.
  • Przykład: VectorViewport.island.tsx. Strona wybiera, co pokazuje: <VectorViewport renderer="SVG" sourceFormat="LOCI">.

Najmniejsza wyspa i jej użycie:

// site/client/Licznik.island.tsx
import { useState } from "preact/hooks";
import { island } from "@/web/island.ts";

export default island( import.meta.url, function Licznik( { start }: { start: number } ) {
	const [ n, ustaw ] = useState( start );
	return <button onClick={() => ustaw( n + 1 )}>{n}</button>;
} );

// w stronie albo sekcji
import Licznik from "@/site/client/Licznik.island.tsx";
<Licznik start={0} />

#ZALEŻNOŚCI

  • Bez Node.js, bez npm, bez folderu node_modules.
  • Zależności są w deno.json, w polu imports: z jsr: albo z https://esm.sh/. Skrót @/ to katalog projektu.
  • Przeglądarka dostaje mapę importów z tymi samymi adresami. Serwer i przeglądarka używają więc tych samych wersji, a wersję zmienia się w jednym miejscu.
  • Kod przeglądarki może używać tylko pakietów z listy w web/importmap.ts (dziś: preact, @preact/signals, highlight.js) i tylko z adresów https://. Przeglądarka nie rozumie jsr:.

#DODATKI

  • Listwy. Element z data-listwa="gora" albo data-listwa="dol" (np. GuideBar, FootBar) jest mierzony w przeglądarce. Jego wysokość trafia do zmiennych CSS --listwa-gora i --listwa-dol. Z nich Table liczy wiersze fill1, fill2 …: wysokość ekranu między listwami.
  • Kotwice nagłówków. Title dostaje id z prefiksu i tekstu, np. #wstęp. Powtórzone id dostaje sufiks -1, -2 … (jak w markdown). Po najechaniu na nagłówek pojawia się link #. Własne id można podać atrybutem.
